# Master Defect Registry

Whole-codebase SQA engagement, started 2026-09-26. Severity scale S0 (critical) to S4 (informational). Status flow: OPEN, CONFIRMED, IN PROGRESS, FIXED, REGRESSION TESTED, VERIFIED. Evidence for every entry is an automated test in this repository that fails on the old behavior and passes on the new. "VERIFIED" means the regression test passed against the real database (and, for SQA-005, against the real compiled contract). Nothing has been deployed yet; deployment verification is a separate step.

## Storage layer findings (S3 / Azure compatibility), all found by driving the REAL AWS CLI against a running server

None of these was caught by the existing unit tests; each was reproduced with `aws` first and is now covered by a regression test (`sqa-s3-presign`, `sqa-s3-store`, `sqa-s3-realclient`).

| ID | Sev | Defect | Root cause | Fix | Status |
|---|---|---|---|---|---|
| SQA-022 | **S1** | Every object key containing a space, parenthesis, plus, ampersand, percent or non-ASCII character failed authentication (`SignatureDoesNotMatch`), for uploads and downloads alike. | The SigV4 canonical URI encoded `url.pathname`, which is already percent-encoded, a second time. | Decode each segment, then encode once (the form botocore signs). Pinned by a header-signed request captured from the real AWS CLI. | REGRESSION TESTED |
| SQA-017 | **S1** | With Pinata blocked ("plan usage limit"), every S3 and Azure write returned 500 even though a second provider was configured. | `putS3Object` used one provider; the existing fallback helper was only used by NAS backup. | Preferred provider first, then every other configured provider (org and wallet stores). Pinning precedes any database write, and reads use the stored provider. | REGRESSION TESTED |
| SQA-016 | **S1** | Completing a multipart upload larger than about 24 MB failed (`QueryExceededMemoryLimitNoDiskUseAllowed`). | Parts (base64 bodies) were sorted inside the database; no index on `(uploadId, partNumber)`. | Sort in code; unique index added. | REGRESSION TESTED (ordering); the 32 MB limit itself is exercised by the 17 MB real-client run only indirectly |
| SQA-018 | **S1** | A client retry during CompleteMultipartUpload wrote the object twice, then answered NoSuchUpload. | Completion takes about a minute (encrypt, shard, pin twice), the SDKs' default read timeout, so clients retry while the first request is still running; nothing claimed the completion. | Atomic claim (`multipartCompletion.js`): one request does the work, retries wait for and return the same result, a failed completion releases the claim, a stale claim is taken over, no parts accepted once completion starts. | REGRESSION TESTED |
| SQA-019 | S2 | `aws s3 presign` URLs (and every SDK presigner) were rejected. | Query-string SigV4 was documented as unsupported. | Implemented and verified (expiry, method and path binding, scope checks). AWS4 verified against real-CLI fixtures; the GOOG4 (X-Goog-*) variant shares the code path but is UNVERIFIED against a Google client. | REGRESSION TESTED (AWS4) |
| SQA-020 | S2 | A ranged or parallel download of a 30 MB object failed. | Every ranged GET fetched and decrypted the whole object again; the CLI issues several in parallel and each took 35 to 60 s. | Concurrent and repeated reads of one immutable version share one fetch (`objectBodyCache.js`); authorization is still checked fresh on every request, so a deleted object is never served from the cache. | REGRESSION TESTED |
| SQA-021 | S2 | Every ranged GET failed the AWS CLI's checksum validation. | 206 responses carried the whole-object `x-amz-checksum-sha256`. | Omitted for partial content, as S3 does. | REGRESSION TESTED (real client) |
| SQA-023 | S2 | The ETag was an internal pin name (`s3-compat:<org>:<key>:<id>:alpha`): non-standard, and it exposed internal identifiers. | ETag was derived from the shard reference. | Content MD5 for single-part objects and `md5-of-part-md5s-N` for multipart, as real S3 (rclone, Terraform and sync tools rely on it). Objects written before this change keep their old value. | REGRESSION TESTED (real client) |
| SQA-024 | S2 | Test files that leave the database connection open never exited after their tests passed, so a full run hung (found on `ai-tool-registry`, `s3-compat-store`, `s3-compat-capabilities`; would hang CI). | Roughly 40 test files have no explicit connection close. | `npm test` now runs with Node's `--test-force-exit`, which exits once every hook (including each file's own cleanup) has finished. A first attempt, a preloaded hook that closed the connection, ran BEFORE the files' own cleanup and made those cleanups silently fail (three throwaway orgs leaked); it was replaced. `ai-tool-registry` now exits in 3 s. | VERIFIED |
| SQA-025 | S3 | During this engagement both configured providers refused writes at once (Pinata plan block, Filebase 500-pin free limit), so every storage write and storage test failed. | No last-resort provider for development and CI. | Opt-in local file provider (`INAYA_LOCAL_PIN_DIR`), never active on Vercel, listed last so it is only a fallback. | REGRESSION TESTED |

A read-only audit found 204 pins belonging to organizations that no longer exist; 118 of them are referenced by no stored document. Nothing was deleted. Deleting an object never unpins the provider copy, which is the underlying leak (OPEN, see below).

| SQA-026 | **S1** | Every PDF render on Vercel (Document Automation, Business Event Passport export) failed: `Cannot find module '#standard-fonts/Helvetica'`. Found by the first live generation. | pdfkit was bundled but loads its fonts through a build-time absolute path and a package `imports` alias the file tracer cannot follow; the font data was not shipped. | pdfkit kept external; its font data (with the shared `chunks/` helper) listed in the tracing includes for all API routes. Verified in a simulated function holding only the shipped files (standard-fonts PDF and an Arabic PDF with the bundled Noto font). | `test/pdf-serverless-config.test.mjs` (config guard) plus the simulation; confirmed live in production (English Preview and Generate, 2026-09-27) | VERIFIED (English); Arabic/Urdu live check still open |

## Test infrastructure improvement

`test/_next-hooks.mjs` now resolves the `@/` alias and extensionless imports the way Next does, so route files that use them can be imported by the plain-Node test runner. Before this, routes such as the bridge and node-assignment routes were untestable.

## Open evidence-backed risks (not fixed; each needs a decision or a larger change)

| ID | Sev | Risk | Why it is open |
|---|---|---|---|
| R-1 | S2 | `metadata/list-files`, `list-folders`, `list-shared-with-me`, `get-shared-file-key` are unauthenticated: anyone can list any wallet's file names, sizes and share records by address. Writes are signature-gated. | Documented as an intentional "trust tier", and the custody SDK depends on unauthenticated reads. Signing reads would break the SDK's public contract. ## Baseline blockers (environment, not defects)

- `inaya-migration-agent` tests need a running dev server on `localhost:3000` (they call the app over HTTP): 5 of 9 pass without it. To be run against a local server in the end-to-end phase.
- `inaya-drive-core` has no tests; `terraform-provider-inaya` has no test files.
- Hardware and OS verification of desktop, mobile and drive helpers is not possible from this environment and will be recorded as UNVERIFIED.
